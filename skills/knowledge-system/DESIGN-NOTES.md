## What we're building

A knowledge-management system that lets a coding agent accumulate durable, hard-won
knowledge about a repo *inside* that repo, so it gets better every session. A skill
(Claude Code / Windsurf) is the interface to it. A companion skill manages/maintains
it (modeled on the `second-brain` project).

## Locked decisions

1. **North star: compounding recall.** The win is the agent visibly recalling a
   hard-won fact from earlier sessions. Retrieval-efficiency is a hard *constraint*
   (consumer is the agent mid-task, on a token budget), not the headline.
2. **Truth via manual lint.** Self-maintaining accuracy is handled by a `lint`
   operation the user runs on demand (surfaces/fixes staleness + contradictions),
   not by automatic enforcement.
3. **Retrieval substrate: flat index that shards.** A single `index.md`, *generated
   from card frontmatter* (never hand-maintained), that `lint` shards by topic once
   it crosses a threshold (~150 cards). Flat now for perfect recall; tiered later for
   token economy; zero migration cost because the index is a build artifact.
4. **Card unit: atomic fact card.** One card = one durable, self-contained fact.
   Reasoning: coding agents issue point queries wanting the smallest complete answer;
   atomic maximizes signal density in the context window; atomic keeps the flat index
   a *faithful router* (one-line summary is near-lossless); trust is per-fact; capture
   is one-card-cheap. Breadth ("everything about auth") is served by the topic-shard,
   not by fattening the unit. Full generated-synthesis pages are a deferred upgrade.
   Rejected: accreting topic/entity pages (optimizes for human browsing, not the agent).
5. **Two shapes: atomic cards + a flat glossary.** Access pattern decides the unit.
   Fact cards are point-query targets (selective, under-budget) -> atomic, full frontmatter,
   types `gotcha | rationale | architecture | operational`. A glossary is a read-whole
   ambient resource -> ONE flat `CONTEXT.md` per context (term -> tight definition + `_Avoid_`
   synonyms), NO per-term frontmatter (confidence/refs/status are meaningless or wrong for a
   definitional fiat; synonym-collision sharpening only works with terms adjacent). `glossary`
   is therefore DROPPED from the card `type` enum and becomes a sibling artifact. The generated
   index lists `CONTEXT.md` as a first-class entry (pull whole vocabulary on entering a domain)
   and lists cards individually. Cards link terms via `[[term]]`; canonical home is CONTEXT.md.
   Glossary shards like cards do: past a few dozen terms, lint splits into per-topic CONTEXT.md
   under a `CONTEXT-MAP.md` (same zero-migration sharding rule). Adapted from grill-with-docs.
6. **Capture-worthiness rubric.** The bar is "no" — a bad card is worse than no card (it
   dilutes signal and erodes trust until the agent re-verifies everything = net-negative).
   CORE TEST, generalizing the grill-with-docs three-gate test into two axes:
   - **Hidden** — can a future agent cheaply re-derive this from the working tree, a search,
     or general knowledge it already has? If yes, don't capture.
   - **Costly** — if the agent doesn't know it, does it waste real time or take a wrong path?
     If low-stakes, don't capture.
   **Capture iff Hidden AND Costly.** The other quadrants: Hidden+cheap = trivia (skip);
   not-Hidden+Costly = the code already says it, a code comment beats a card (skip).
   PER-TYPE operationalization of Hidden×Costly:
   - `rationale`: the three-gate test verbatim (hard to reverse · surprising without context ·
     real trade-off) + name the rejected option in `summary`/`tags` so "try B" routes to it.
   - `gotcha`: Hidden = code reads like X but does Y / has a non-local effect; Costly = a caller
     trusting the obvious reading ships a bug. If the signature/types encode it, skip.
   - `architecture`: Hidden = emergent/cross-cutting invariant visible from no single file;
     Costly = violating it breaks things non-locally.
   - `operational`: Hidden = command/sequence undiscoverable by reading code (runbook/env/tribal);
     Costly = getting it wrong burns time or breaks an environment.
   MECHANICS: (a) dedup before write — scan index for same topic+claim, UPDATE/supersede rather
   than duplicate (duplicates are the #1 bloat source); (b) confidence floor — worthiness is
   separate from truth-certainty; if worthy but unconfirmed, HOLD, don't write; no cards < ~5/10;
   (c) cards pay rent — never-retrieved cards are pruning candidates (lint's job), capture mindset
   is "earn ongoing rent," not "get in once."
   CAPTURE MODEL = **hybrid** (LOCKED). Agent applies the rubric to filter hard (most things never
   get proposed), drafts surviving candidates inline as they arise, then at END OF SESSION presents
   ONE batched approval: "I'd capture these N: … [y/n/edit]." One gate, not N interruptions. Rubric
   does the heavy lifting; user is the cheap final backstop against bloat. A config flag can later
   flip to full-auto once the user trusts the rubric.

7. **Retrieve operation.** Routing is the LLM's job, not a vector DB's: the agent reads a
   cheap markdown index of one-line summaries and judges relevance semantically. NO embeddings/
   vector store/infra (dependency-free, inspectable; this is why dec. 4's near-lossless summary
   is load-bearing). Index growth is handled by dec. 3 sharding.
   PIPELINE (4 stages):
   - Stage 0 Trigger — three shapes: task-start (big pull), decision-check (loud rationale gate),
     on-demand point query (~1 card).
   - Stage 1 — load the glossary whole (`CONTEXT.md`, via `CONTEXT-MAP.md` if multi-context).
   - Stage 2 — route through the index: top-level index (TOC of topic-shards) -> relevant shard
     index -> candidate card ids by `summary`/`topic`/`tags` match. Only selected cards load full.
   - Stage 3 — load selected card bodies under budget, ranked
     `relevance > confidence > status (active>stale, never deprecated unless asked) > recency`.
   BUDGET = "smallest set that answers the task," soft top-K cap (~5-7 cards). NOT a hard token #.
   DECISION A: **rationale cards are exempt from the cap** — a rationale matching an approach
   decision gets a reserved slot, surfaced even over budget (missing one = the system's most
   expensive failure: silently re-trying rejected design B).
   DECISION B: **decision-check is a mandatory pre-action gate**, not a passive lookup. Before the
   agent proposes/switches an approach on topic T, filter index to `type: rationale` on T; any hit
   is surfaced to the user BEFORE proceeding. Structural, because it's the flagship demo.
   GUARDRAIL: hit-count does NOT feed retrieval ranking (avoid rich-get-richer / new-card
   starvation). Hit-tracking is now OPTIONAL analytics only (see decision 8) — retrieve stays
   read-only on the shared base by default.

8. **Lint operation — hit-free.** Lint's power is correctness signals, not usage. It needs
   no hit-tracking, and tracking is demoted to an optional local-only add-on (below).
   Reframed pruning philosophy: **prune by wrongness, not coldness.** A cold-but-correct card
   costs ~one index line (sharding bounds it) and never costs retrieval budget — "rarely used"
   is a weak eviction reason. The cards that hurt are WRONG ones, all caught structurally:
   - Staleness via ref-resolution (PRIMARY): resolve each `ref` against the working tree;
     gone/moved code -> flag. Targets wrong cards, not quiet ones.
   - Contradiction sweep: LLM reads a topic-shard, flags mutually exclusive claims, forces a fix.
   - Dedup/merge: catch near-duplicate summaries capture-time dedup missed.
   - Status hygiene: `superseded`/`deprecated` -> archive.
   - Confidence + age review: old + low-confidence + never-confirmed -> re-examine.
   - Rationale-staleness: re-examine when a rationale's "valid-while" constraint changes
     (constraint-driven, not usage-driven). [see rationale-staleness parking item]
   - Sharding: count cards per topic, split index at threshold (dec. 3).
   - Orphan/connectivity: zero `refs` + no `related` + unlinked -> flag.
   Dropping coldness-pruning also means a cold `rationale` card is fine — it's insurance,
   correct and waiting.
   OPTIONAL HIT-TRACKING ADD-ON (off by default, lint never depends on it): if enabled, retrieve
   buffers events and flushes at session end to a LOCAL, GITIGNORED `.knowledge/retrieval-log.jsonl`
   (one line per retrieve: ts, task_topic, card_ids, rationale_gate_fired, empty). A `stats` view
   aggregates into a generated, also-local `STATS.md`. Surfaces: hot cards (= north-star meter:
   compounding recall, measured), empty-retrieves-by-topic (knowledge-gap finder), rationale-gate
   fire count (flagship-value meter). Local-only = zero merge risk in a team; never on the shared
   hot path. Not required for any core operation.

9. **Capture operation.** The mirror of retrieve; worthiness is already settled (dec. 6), this
   is the hybrid flow's mechanics. THREE STAGES:
   - Stage 1 Inline draft — fires on TYPE-SHAPED trigger moments (the inverse of dec. 6's
     per-type operationalization): a choice between real alternatives -> `rationale`; expected X,
     code did Y -> `gotcha`; relied on a non-local invariant -> `architecture`; learned a
     command/sequence by trial -> `operational`; user STATED something non-obvious ->
     `source: user-stated`. Drafts persist to a LOCAL, GITIGNORED `.knowledge/inbox/` (survives
     compaction/crash; pre-approval so out of the committed base). Capture `refs` + `source` AT
     THE MOMENT, not at approval (the agent knows the line then; won't at session end).
   - Stage 2 End-of-session batch — fires at a task-completion boundary, an explicit command, or
     a pre-compaction safety flush; NEVER a mid-task nag. ONE interaction for N drafts:
     `[a]ll / [n]one / per-item [k]eep [d]rop [e]dit`. Each row shows summary + type + topic +
     the one-line Hidden×Costly justification. Full body generated on approval; edit after only
     if wanted. Lightweight.
   - Stage 3 Materialize — fill auto-derivable fields (`id` slug, created/updated, `status:active`,
     `source`, `confidence` gated by floor; `refs` already from the draft). DEDUP against index
     before writing: same claim + new evidence -> UPDATE existing; genuinely new -> CREATE;
     contradicts existing -> SURFACE AT CAPTURE (decision below). Then regenerate the affected
     topic-shard of the index from frontmatter (dec. 3, build artifact). Localized, cheap.
   GLOSSARY capture rides the same flow, writing to `CONTEXT.md` instead of a card (lighter).
   CONTRADICTION HANDLING = **surface at capture** (LOCKED). When a draft contradicts an existing
   card, raise it then ("contradicts card X; reconcile or supersede?") — cheap (index already
   loaded), human in the loop, freshest moment to catch it. Lint still does the BROAD sweep for
   contradictions capture didn't witness; this handles the one staring you in the face.

10. **Rationale card body sub-structure.** Follows from dec. 4 + dec. 6: design A lives in the
    code (NOT Hidden) — B and why-it-lost leave zero trace (maximally Hidden). So the body does
    NOT re-document A; it spends its weight on the irrecoverable part. Structure = the generic
    `Fact / Why / How` triad, specialized:
    - **Decision.** One line: the question + chosen option NAMED, not elaborated (code shows the
      detail). (= Fact)
    - **Rejected.** Each rejected option + the SPECIFIC reason it lost. THE payload — the only
      irrecoverable content; the body's weight goes here. (= Why it matters)
    - **Valid while.** The condition(s) that keep the rejection binding; when they change, B is
      back on the table. (= How to apply; also lint's staleness trigger, below)
    NO separate "Chosen" section (folds into Decision; don't re-document A — dec. 4). If A itself
    has a non-obvious trap, that's a SEPARATE `gotcha` card (atomicity), not weight here.
    ROUTING REQ (locked from parking lot): `summary` + `tags` must NAME the rejected option(s) so a
    future "let's try B" query routes here even though B has no code to anchor to.
    COUPLED ITEMS RESOLVED:
    - Surfacing format ([~] item): the body dictates the surface. When the decision-check gate
      (dec. 7B) fires, show three lines — Decision + the Rejected reason FOR THE TEMPTED OPTION +
      Valid-while, then ask before proceeding ("⚠ Prior decision: chose X over B (rejected: …).
      Still valid while …. Proceed with B anyway?").
    - Rationale-staleness lint: `Valid while` is the constraint lint watches. Lint can't auto-detect
      most constraint changes, so it SURFACES each rationale's Valid-while line for human
      re-confirmation on a topic pass (constraint-driven, human-in-loop) — unlike ref-staleness
      which auto-resolves against the working tree.

11. **Granularity rule — "how atomic is one fact."** Atomic = INDIVISIBLE-WITHOUT-LOSING-A-CONSUMER,
    NOT minimal. One card = the LARGEST fact still retrieved, trusted, and invalidated as a single
    unit. The test is the three core ops, each pinned to an existing frontmatter field — fork any
    one → split:
    - retrieve: would a point query ever want one claim WITHOUT the other? (`summary`)
    - trust: do the parts have different certainty/origin? (`confidence`/`source`)
    - lint: would the parts go stale at DIFFERENT times? (`refs`/`status`)
    LINGUISTIC TELL (fast capture heuristic): write summary as one sentence. "and" joining two
    independently-useful claims → two cards; a single claim + its CONSEQUENCE ("…so callers must…",
    "…because X") → ONE card (the consequence is part of the fact; `How to apply` exists for it —
    never split a claim from its own fix).
    DEFAULT LEAN = SPLIT. Asymmetry: a too-small pair linked by `related` + shared `topic` still
    retrieves together via the shard (dec. 4 — breadth is the shard's job), and lint dedup/merge
    (dec. 8) fuses cheaply later; a too-fat card needs a rewrite to split and breaks the near-lossless
    summary. Split is reversible, merge-by-hand isn't.
    FLOOR (guards over-splitting): a card must be self-contained — useful/intelligible retrieved
    ALONE. A fragment that only makes sense beside its sibling failed the test → it's one fact, keep
    together. (A rationale with N rejected options stays ONE card per dec. 10: one decision, one
    Valid-while fate.)
    DEDUP FALLS OUT (second consumer): two drafts are "the same claim" iff they'd share a summary line
    AND a staleness fate (same primary ref) — same assertion + new evidence → UPDATE; different ref or
    consequence → CREATE (+ optional `related`). Gives capture-time dedup (dec. 6/9) a concrete
    definition of "same claim." Glossary terms exempt (one line each in CONTEXT.md, dec. 5).

12. **Companion skill scope — two skills, single-writer invariant.** The four ops sort by
    consumer + invocation (matches the CLAUDE.md "interface skill + companion management skill"
    intent):
    - IN-LOOP skill (the interface): consumer = coding agent mid-task; AMBIENT (fires on dec. 7 §0
      retrieve triggers / dec. 9 §1 capture-draft triggers); lightweight, on a token budget. Owns
      `retrieve` + capture-draft (stage 1 only).
    - MANAGEMENT skill (the companion, second-brain-modeled): consumer = human maintaining the base;
      DELIBERATE (user-invoked periodically); heavy (LLM sweeps the whole base). Owns `materialize`
      (capture stage 2/3) + `lint` (dec. 8) + `stats` (optional, dec. 8) + one-time `init` scaffold.
    ORGANIZING INVARIANT = SINGLE WRITER TO THE COMMITTED BASE (the real reason to split):
    - In-loop READS the committed base (retrieve) and WRITES only to the local gitignored inbox
      (capture stage 1). It never mutates a committed card → the constantly-firing ambient reflex
      carries ZERO merge risk and can't corrupt the shared base (why dec. 9's inbox is local+ignored).
    - Management is the ONLY mutator of the committed base (materialize, dedup, shard, status,
      index regen, lint fixes) → every base mutation goes through one deliberate, reviewable gate.
    The inbox is the staging area BETWEEN the two skills; the end-of-session batch approval (dec. 9
    §2) is the HANDOFF point (drafts accumulate → user approves → management materializes), which is
    why `materialize` lives in management (base-mutating + deliberate) despite being capture's back
    half. Exact Claude Code wiring of "ambient" (auto-loaded behavioral contract vs. on-demand
    invoke) is an implementation note, out of design scope.

13. **`convention` type — DROPPED (confirmed).** A convention ("hooks named use-X", "tests beside
    source") is grep-able / visible in the file tree → NOT Hidden → fails the dec. 6 rubric. Its two
    real homes already exist: naming/vocabulary → the glossary (CONTEXT.md, dec. 5); a genuinely
    undiscoverable + costly-to-violate convention → an `architecture` card (emergent cross-cutting
    invariant — exactly that type's purpose). No gap. The `type` enum stays the locked four
    (`gotcha | rationale | architecture | operational`).

14. **`source` enum gains `ticket:<id>`.** A fact found during ticket work can cite the ticket as
    its richest provenance (carries the surrounding discussion for a human refreshing context —
    especially valuable on `rationale`). It belongs in `source`, NOT `refs`: `refs` are
    lint-resolved code anchors, and a ticket can't resolve against the working tree (would create
    permanent false staleness); `source` is never lint-checked, so a dead/archived ticket link
    breaks nothing. Vendor-neutral `ticket:<id>` (Jira `ticket:PROJ-1234`, Linear, issue trackers),
    not `jira:`. `source` stays single-valued = the single richest origin; artifact pointers beat
    discovery modes, priority `ticket > pr > commit > user-stated > observed > session` (the trust
    signal `user-stated` carried is already encoded in `confidence`).

15. **File layout — one namespaced root `.knowledge/`.** Resolves "where do committed artifacts
    live" + "`index.md` is too generic." One dotted root (signals tool-metadata, namespaces generic
    filenames) with a committed zone (`index.md`, `topics/` shard indexes, `cards/`, `CONTEXT.md`)
    and a LOCAL gitignored zone (`inbox/`, `retrieval-log.jsonl`, `STATS.md`) — making the
    single-writer invariant (dec. 12) three `.gitignore` lines. CARDS STAY FLAT in `cards/` even
    when the index shards: sharding reshuffles only generated index files (`index.md` ->
    `topics/*.md`), card files never move (`refs`/`related` point by `id`, not path) — this is what
    makes dec. 3's "zero migration cost" literal. Root name is a convention (nothing references it
    by content), changeable.

16. **Delivery model — two surfaces; proactive ⇒ contract.** Sharpens dec. 12's punt ("how
    'ambient' is achieved is an impl note") — turns out it's partly a DESIGN constraint, because it
    determines whether the flagship works. Two delivery surfaces: (1) an always-loaded agent
    contract (`CLAUDE.md` / Windsurf `guideline.md` / etc.), (2) human-invoked workflows
    (`materialize`/`lint`/`stats`/`init`). ALLOCATION RULE = a reflexive behavior CANNOT be an
    opt-in skill (agent might not invoke it); the decision-check gate (dec. 7B) is MANDATORY, so it
    + retrieve-on-task-start + capture-draft triggers MUST live in the always-on contract; the
    deliberate ops are invoked workflows. (= dec. 12's ambient/deliberate split at the delivery
    layer.) CONSTRAINT: the resident contract MUST stay minimal — it costs tokens every session, so
    it's a thin trigger-table (pointer to `.knowledge/` + when-to-do-what), NOT the spec; heavy
    detail loads on demand from index/cards (retrieval-efficiency north star). PORTABILITY: contract
    is env-agnostic markdown, only the injection point differs; an `init` workflow installs both
    surfaces. DEFERRED to implementation (doesn't feed back into the model/operations — packaging):
    exact snippet wording, per-env skill/workflow formats + command names, `init` install mechanics.

17. **Monorepo layout = hierarchical per-package (supersedes dec. 15's single-root sketch).**
    Surfaced in eng review: the first real deployment is a monorepo, and the glossary is already
    per-package (root `CONTEXT-MAP.md` + a `CONTEXT.md` per app/lib) by STRUCTURE, not by volume.
    Cards + index follow the same shape: each app/lib has its own `.knowledge/` (CONTEXT.md + local
    index + cards + gitignored inbox); the root `.knowledge/` holds the CONTEXT-MAP, a root
    AGGREGATOR index, and cross-cutting cards only. RULES: a card lives in the package its `refs`
    point into (multi-package refs → cross-cutting → root); single-writer invariant holds per store;
    locality payoff = a package's knowledge travels with its code (move the lib, move its cards;
    refs stay in-package); cards stay flat per `cards/` so v2 volume-sharding is still zero-migration.
    `.gitignore`: `**/.knowledge/inbox/`. Chosen over single-root (rejected: knowledge not colocated,
    a moved lib orphans its cards) and a hybrid root-cards/per-pkg-glossary (rejected: inconsistent).

18. **Monorepo retrieval = dual trigger (root TOC breadth + file-trace depth).** A 4th Stage-0
    trigger added to dec. 7. (a) ROOT AGGREGATOR INDEX is always read = the complete cross-package
    TOC of one-line summaries — the breadth safety net that catches relevant facts in packages the
    agent never opens (e.g. "we abandoned libs/legacy-auth"). (b) FILE-TRACE (user's idea, chosen
    over dependency-graph parsing): opening/tracing into a file under a package's subtree loads that
    package's `.knowledge/` (local index + CONTEXT.md) before trusting the code, once per package per
    session — lazy, precise, piggybacks on reading the file, no dep-graph parser. Trace alone misses
    untouched-but-relevant packages; root TOC alone lacks local depth; together they cover both.
    Ranking prefers current-package cards at equal relevance. Both are reflexive → live in the
    always-on contract (dec. 16). Forward-compat: file-trace is what later lets the root TOC slim to
    per-package digests (v2 optimization); v1 keeps the complete root TOC (full recall).

19. **v1 / v2 scope split (eng-review outcome).** v1 = smallest system that proves compounding
    recall + validates the one risky bet (does the always-on contract reliably fire the agent's
    reflexes?). SHIPS IN v1: atomic cards + schema; flat per-package index + root aggregator;
    retrieve + rationale decision-gate; dual retrieval (root TOC + file-trace); always-on contract;
    FULL capture loop (in-flight draft → gitignored inbox → batched approval → materialize — NOT
    deferrable: in-flight draft is the only moment refs/reasoning are alive, and the inbox is the
    buffer that lets capture happen without interrupting flow); glossary INCL. CONTEXT-MAP sharding
    (monorepo needs it day one); hierarchical per-package layout; `rationale`+`gotcha` machinery; ONE
    management skill + contract. DEFERRED TO v2: entire lint (dec. 8 — VERIFIED decoupled: capture
    owns dedup/contradiction/index-regen at write time, retrieve only reads, so loops work without
    it; cost = no correctness-decay protection, acceptable at low volume); stats add-on; card-index
    volume-sharding (~150); per-type machinery for `architecture`/`operational` (tags only in v1);
    standalone in-loop skill (contract covers reflexes); rich per-item capture-edit UX; root-TOC →
    per-package-digest slimming. FIRST BUILD STEP = an eval proving the agent fires the decision-gate
    + file-trace trigger (behavioral, not unit-testable) before building anything else.

## Flagship use case: decision rationale ("why we rejected design B")

The highest-value card type is `rationale`, because rejected-design reasoning is the
ONE class of knowledge that leaves zero trace in the code and is unrecoverable once
memory fades. Code shows what was built (design A), never what was rejected (B) or why.
Scenario: ship feature with design A over B for reason XYZ -> persist a rationale card
-> 3 months later a related bug/feature tempts the agent toward B -> the system must
surface the prior decision and alert the user BEFORE switching, not silently override.

This is where the system shines and should be a headline demo. Implications captured
in the parking lot below.

## Prior art: grill-with-docs (Matt Pocock)

Source: aihero.dev/grill-with-docs + the 3 md files in mattpocock/skills. Independent
convergence on our core bet (durable repo knowledge as in-repo markdown, token economy
as the payoff). Structure = two artifacts + an interview:
- **CONTEXT.md** — pure ubiquitous-language glossary. Tight, opinionated (`_Avoid_:` lists
  synonyms), explicitly NO implementation details. Read whole; no index.
- **ADRs** (`docs/adr/000N-slug.md`) — one-paragraph "why we decided X" records. This IS
  our `rationale` card. Near-zero ceremony by design.
- **The grill** — Socratic interview that writes both artifacts INLINE as decisions
  crystallize ("don't batch these up"), cross-references code, surfaces contradictions live.

What we steal:
1. **ADR three-gate test = our capture-worthiness rubric backbone.** Keep a record only
   when ALL three hold: (a) hard to reverse, (b) surprising without context, (c) the result
   of a real trade-off. Battle-tested. Adopt for `rationale`, generalize for other types.
2. **Glossary scope rule = the non-obviousness filter.** "Only terms specific to THIS
   context; general programming concepts don't belong." The one question: is this unique to
   this repo, or knowledge the agent already has?
3. **Capture inline, at moment of resolution** (not only an end-of-task sweep) + **lazy file
   creation** (write a file only when there's something to write = anti-bloat by construction).

What we add over it (our value-add): a retrieval layer. grill-with-docs scales only to
"read the whole CONTEXT.md + whole adr/ dir" — no generated index, no sharding, no point
queries under budget, no lint/staleness/contradiction sweep across a large base. We are the
version that survives 300 facts.

New tension it surfaces -> see glossary-shape parking item below.

## Frontmatter schema (locked, approved 2026-05-31)

One atomic fact card = one `.md` file. Only six fields need human/agent judgment
(title, summary, type, topic, confidence, optionally tags/related); the rest are
auto-derivable at capture time.

```markdown
---
id: auth-session-swallows-cookie-errors      # kebab slug = filename
title: Session validation swallows expired-cookie errors
summary: validateCookie() returns undefined (not throw) on expired cookies; callers must null-check.
type: gotcha            # gotcha | rationale | architecture | operational  (LOCKED enum, see dec. 6)
topic: auth             # ONE primary topic = shard key
tags: [session, error-handling, cookies]
confidence: 8           # 1-10; below ~5 -> don't write (dec. 6 floor)
status: active          # active | stale | superseded | deprecated  (lint-managed)
created: 2026-05-31
updated: 2026-05-31
source: observed        # observed | user-stated | session | commit:<sha> | pr:<n> | ticket:<id>  (dec. 14)
refs:                   # load-bearing for lint staleness; zero refs = lint warning
  - src/auth/session.ts:47
  - sym:validateCookie
related: [auth-login-redirect-flow]
supersedes: null
---
**Fact.** ...
**Why it matters.** ...
**How to apply.** ...
```

- `summary` is the index router line (must be near-lossless — dec. 4). `title` is the
  human label. Kept separate on purpose.
- `refs` is load-bearing: it's how `lint` detects staleness (resolve each ref against the
  working tree). A `sym:` ref is symbol-anchored (survives line moves better than file:line).
- Body mirrors the user's ~/.claude memory format (Fact / Why / How to apply).
- RESOLVED: `convention` as a 5th type is DROPPED (dec. 13) — grep-able → not Hidden; folds into
  the glossary or an `architecture` card. The enum stays the locked four.
